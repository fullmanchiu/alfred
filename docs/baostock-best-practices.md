## 关键发现

### 2. `rs.next()` 使用规范

**必须配合 `rs.get_row_data()` 使用**

```python
# ✅ 正确：消费数据
while rs.next():
    row = rs.get_row_data()
    # 处理 row...

# ❌ 错误：只计数，不消费数据
while rs.next():
    count += 1  # 会导致无限循环！
```

**原理**：`rs.next()` 移动游标，`rs.get_row_data()` 消费当前行数据。不消费数据会导致游标无法移动。

## 性能优化建议

### 3. 最佳实践

**推荐方案：单次登录 + 大批次获取**

```python
def fetch_kline_optimal(code, start_date, end_date):
    """最优K线获取方案"""
    # 添加前缀
    if code.startswith('6'):
        bs_code = f"sh.{code}"
    else:
        bs_code = f"sz.{code}"

    # 单次登录
    lg = bs.login()
    try:
        # 一次性获取完整数据
        rs = bs.query_history_k_data_plus(
            bs_code,
            "date,code,open,high,low,close,volume,amount",
            start_date=start_date,
            end_date=end_date,
            frequency="d",
            adjustflag="3"
        )

        if rs.error_code != '0':
            raise Exception(f"查询失败: {rs.error_msg}")

        # 完整读取所有数据
        data = []
        while rs.next():
            row = rs.get_row_data()
            data.append(row)

        return data

    finally:
        bs.logout()
```

**性能对比**：
- ❌ 分批获取：11.690秒/股
- ✅ 一次性获取：0.862秒/股
- **提升：13.6倍**

## 常见问题

### 6. 调试经验

#### 根本原因

**卡住的真正原因**：不消费 `rs.get_row_data()`

| 代码 | 结果 | 原因 |
|------|------|------|
| `while rs.next(): count += 1` | ❌ 无限循环 | 未消费数据 |
| `while rs.next(): row = rs.get_row_data()` | ✅ 正常 | 消费数据 |

**结论**：与数据量大小无关，关键在于是否消费数据。

#### 已排除的问题

**1. 代理问题**
- 症状：连接失败
- 原因：系统代理 127.0.0.1 阻止连接
- 解决：关闭代理后恢复

**2. 日期值问题**
- 症状：无数据返回
- 原因：日期格式错误或超出范围
- 解决：使用 `YYYY-MM-DD` 格式

**3. 错误方法调用**
- 症状：方法不存在
- 原因：调用了 `rs.get_fields()`（不存在）
- 解决：使用 `rs.get_row_data()`

**4. 数据列索引错误**
- 症状：获取错误字段
- 原因：`row[0]` 是日期，`row[1]` 是代码
- 解决：使用正确的索引或字段名

#### 常见错误

**错误1：只计数不消费数据**
```python
while rs.next():
    count += 1  # ❌ 无限循环
```

**错误2：条件中限制 + break**
```python
while rs.next() and count < 100:
    count += 1  # ❌ 触发bug
```

**正确做法**：完整消费数据
```python
while rs.next():
    row = rs.get_row_data()  # ✅ 必须消费
    # 处理数据
```

#### 多进程问题与解决

**问题**：进程越多失败率越高（重试前：2进程92%，4进程82%）
- **原因**：baostock服务端对同一IP多会话有限制，会话被强制失效
- **非竞争问题**：每个进程处理不同股票，不是竞争同一资源

**解决**：重试机制
```python
def process_worker(codes, start_date, end_date, process_id, result_queue, max_retries=2):
    """进程工作函数 - 带重试机制"""
    lg = bs.login()
    total_retries = 0

    try:
        for code in codes:
            retry_count = 0
            success = False

            while not success and retry_count <= max_retries:
                if retry_count > 0:
                    # 重新登录
                    bs.logout()
                    time.sleep(0.5)
                    lg = bs.login()
                    total_retries += 1

                rs = bs.query_history_k_data_plus(...)
                if rs.error_code == '0':
                    success = True
                    # 处理数据...
                else:
                    retry_count += 1
    finally:
        bs.logout()
```

#### 最终推荐

**✅ 推荐：4进程 + 重试机制**
- 100%数据完整性（重试保证）
- 比2进程快 **1.63倍**（节省9.2秒）
- 吞吐量 **22.02股/秒**
- 错开登录时间（进程间隔0.3秒）减少会话冲突

**关键点**：
- ✅ **进程隔离**：每个进程有独立的baostock会话
- ✅ **重试机制**：失败时重新登录后重试，保证100%数据完整性
- ✅ **错开登录**：避免同时登录减少冲突
- ❌ **多线程不可用**：baostock不支持多线程，会导致数据混乱

**瓶颈分析**：
- CPU使用率低（峰值3.5%），内存占用低（~60MB）
- 瓶颈在**网络I/O**，受baostock服务端带宽限制
- 8进程没有进一步提升（重试开销抵消并行优势）

## 总结

**核心原则**：
1. **单次获取完整数据** - 避免分批
2. **必须消费数据** - 调用 `rs.get_row_data()`
3. **单次登录即可** - 不需要每次查询都登录
4. **并发使用多进程** - 多线程会导致数据混乱

**性能优化**：
- 速度 = API调用次数的倒数
- 减少查询次数 = 提升性能
- 年批次比周批次快 13.6 倍
- 多进程并发可进一步提升吞吐量

**并发方案选择**：
- 单线程：稳定，适合少量股票
- 多线程：❌ 不可用，会导致数据混乱
- 多进程：✅ 推荐，进程隔离 + 进程内保持登录
